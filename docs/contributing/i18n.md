# Internationalisation (i18n)

Paisa uses [`svelte-i18n`](https://github.com/kaisermann/svelte-i18n) to translate the SvelteKit UI. The framework is wired up in `src/lib/i18n/` and bootstrapped from `src/routes/(app)/+layout.ts` once `/api/config` resolves, so the very first paint has the right bundle loaded.

This page covers the conventions a contributor needs to know to add translations safely. It is intentionally short — the rules are simple.

## Locale resolution

The active locale is chosen in this order:

1. `USER_CONFIG.locale` from `paisa.yaml` (set on the **More → Configuration** page).
2. `navigator.language` (the browser's preferred locale).
3. `en` (hard fallback).

Unknown locales (e.g. a typo, or a locale we have not translated yet) still render — `svelte-i18n` falls back to `en` automatically for any missing keys.

## File layout

```
src/lib/i18n/
├── index.ts           # registers locales, exposes `_`, `locale`, `waitLocale`, `initI18n`
└── locales/
    ├── en.json        # source of truth
    └── zh-CN.json     # translated bundle
```

Locale tags use BCP-47 (e.g. `en`, `zh-CN`, `en-IN`). They must match the values shipped by the backend's config schema (`internal/config`).

## Key naming

Keys are dot-separated and follow `<page-or-area>.<sub-area>.<key>`. Examples:

| Key                          | Used at                              |
| ---------------------------- | ------------------------------------ |
| `app.title`                  | Application-wide brand name          |
| `nav.dashboard`              | Top navbar Dashboard link            |
| `expense.monthly.title`      | Heading on the Expense › Monthly tab |
| `config.section.preferences` | Section heading in the config page   |

Rules of thumb:

- The first segment is the **page or shared area** (`nav`, `app`, `expense`, `assets`, `config`, …).
- The leaf key is **what the string is**, never its English content. Renaming a button label should not require renaming the key.
- Keep keys flat-ish (2–3 segments). Deep nesting hurts readability without much benefit.
- Reuse: if the same label appears in several places, hoist it under `common.*`.

## Adding a new key

1. Add the English entry to `src/lib/i18n/locales/en.json` — this file is the source of truth.
2. Add the matching entry to every other locale (`zh-CN.json` today). Missing keys fall back to `en` at runtime but should not be left missing intentionally.
3. Use it in a component:
   ```svelte
   <script lang="ts">
     import { _ } from "$lib/i18n";
   </script>

   <h1>{$_("app.title")}</h1>
   ```
4. For dynamic placeholders, pass `values`:
   ```ts
   $_("dashboard.greeting", { values: { name: user.name } });
   ```
   …and in JSON: `"greeting": "Hello, {name}"`.

## Adding a new locale

1. Create `src/lib/i18n/locales/<tag>.json` with the same key tree as `en.json`.
2. Register it in `src/lib/i18n/index.ts` next to the existing `register(...)` calls.
3. Add the tag to the locale options exposed by the backend config (`internal/config`) so users can pick it from the UI.
4. Run `make jstest` to make sure no test asserts on a now-stale set of locales.

## Testing

Unit tests live next to the module (`src/lib/i18n/i18n.test.ts`) and run under `bun test --preload ./src/happydom.ts src`. Stick to the same patterns:

- Set the locale explicitly via `initI18n("zh-CN")` then `await waitLocale()` before asserting on translations.
- Reset `locale.set(null)` in `beforeEach`/`afterEach` so tests don't leak state.

## Out of scope

- **Backend strings**: error messages produced by Go handlers are not localised yet. Convention is to keep them in English and let the frontend translate at the boundary.
- **Number / date formatting**: handled by `src/lib/format.ts` (which respects `USER_CONFIG.locale` directly via `Intl` and `dayjs`). Do not duplicate formatting logic in translation bundles.
